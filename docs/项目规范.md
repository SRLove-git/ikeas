# BUZUD 商城项目规范

> 本规范参照企业级研发规范模板制定，并结合本项目实际技术栈（Next.js 16 + React + TypeScript 前端、Java 21 + Spring Boot 3.5 后端、JSON 文件数据）适配。项目所有成员与 AI 协作代理须遵守本规范。

## 1. 项目概述

本项目是 BUZUD 健康产品商城：前台（商品浏览、搜索、购物袋、收藏、订单、客户服务）+ 管理后台（首页、分类、菜单、商品、落地页、订单、客服知识库均表单化编辑）+ 后端 REST API。

核心约束：

- 商品目录**只保留**零售价清单中的 23 个 BUZUD 商品，禁止混入原模板的 IKEA 商品数据。
- 商品零售价以 **SGD（新加坡元）** 为单位，展示统一走 `formatPrice`。
- 前端内容编辑仍以 JSON 文件为唯一入口，`frontend/src/data/` 为源；后端业务数据（用户/购物袋/收藏/订单/客服聊天）与静态内容快照已迁移到 PostgreSQL 16，通过 Flyway 管理表结构、MyBatis-Plus 访问。
- 已推送 GitHub：`git@github.com:SRLove-git/ikeas.git`。

## 2. 编码与风格规范

### 2.1 后端（Java / Spring Boot）

- 遵循《阿里巴巴 Java 开发手册》基础规范：命名清晰、无魔法值、禁止忽略异常。
- 统一分层与包结构（对应现有 `com.ikea.server` 包）：
  - `web`（接口层，等价 controller）
  - `service`（业务逻辑层）
  - `mapper`（数据访问层，MyBatis-Plus Mapper）
  - `entity`（数据库实体）
  - `dto`（接口出入参）
  - `constant`（常量与枚举）
  - `config`（配置）
  - `data`（过渡期 JSON 存储层，数据库落地后废弃）
- 数据访问使用 **MyBatis-Plus**：复杂查询用 `LambdaQueryWrapper` 或 Mapper XML（`#{}` 参数化），禁止在业务代码中拼字符串 SQL。
- 提交前通过 Spotless / Checkstyle 检查与格式化（配置接入见 §15 第一批）。

### 2.2 前端（React + TypeScript / Next.js）

- TypeScript 强类型（strict），禁止 `any`、禁止隐式 `any`。
- React 统一使用 Hooks 写法；函数组件 + 命名导出；服务端组件与 `"use client"` 边界清晰。
- 样式使用 Tailwind 工具类，禁止内联 style（后台动态颜色等少数场景需注释说明）。
- 提交前必须通过 **ESLint + Prettier**：
  - `npm run lint`（ESLint，0 error）
  - `npm run format:check`（Prettier 检查）
  - 可执行 `npm run format` 自动格式化
- **禁止提交带 lint 报错或格式错误的代码。**

### 2.3 数据（JSON 文件）

- JSON 是项目的数据层，编辑必须保持结构合法、字段与既有 schema 一致。
- 禁止直接手工修改后端副本 `backend/src/main/resources/data/`；一律改 `frontend/src/data/` 后执行 `node scripts/export-server-data.mjs` 同步。
- 复杂数据变更（商品批量导入）必须通过脚本或管理后台完成，禁止手工拼写 JSON。

## 3. 命名规范

- 模块/服务：小写 + 连字符（后端服务 `ikea-server`，前端应用 `ai-website-clone-template`），与镜像名、容器名保持一致。
- 接口：RESTful 资源命名，路径小写复数，统一前缀 `/api/v1/`（如 `/api/v1/products`、`/api/v1/orders`）。
- 前端路由：小写 + 连字符（`/cn/zh/cat/buzud-rapid-tests`、`/cn/zh/p/<slug>`）。
- 数据字段：
  - JSON 内统一 camelCase（`productType`、`designText`、`originalPrice`）。
  - 后端 Java 字段与 JSON 通过 Jackson 映射，保持一致命名。
  - 商品 `id` 使用 SKU（13 位数字），`slug` 唯一。

## 4. 目录结构规范

仓库采用类 Monorepo 布局（前后端分目录），当前结构：

```
backend/          # 后端（Java Spring Boot，微服务代码）
  src/main/...    # 源码与 resources/data 数据副本
  Dockerfile
frontend/         # 前端（Next.js，含商城前台 + 管理后台）
  src/
    app/          # 路由页面（前台 + /admin + /api）
    components/   # 组件（含 admin/ 后台组件）
    lib/          # 工具与数据读取（对应 utils）
    data/         # 数据文件（商品/分类/首页/菜单/内容页）
    types/ hooks/ # 类型与自定义 Hooks
  public/         # 静态资源（图片、SEO、字体）
  package.json / next.config.ts 等工程配置
docs/             # 文档（本规范、ADR）
deploy/           # Dockerfile、docker-compose.yml（Docker/CI/CD 配置）
scripts/          # 工具脚本（导入/菜单/导出）
```

页面与路由、菜单、权限一一对应；新增页面时同步更新导航（`frontend/src/data/homepage.json` 的 `navMenuItems`）与菜单数据（`menu-categories.json`）。

## 5. 数据规范

### 5.1 过渡期：JSON 文件（现状）

- **变更管理**：所有数据变更通过管理后台表单或导入脚本完成，禁止手工改线上文件；文件变更由 git 记录，可回滚。
- **金额**：商品价格使用数值类型（number，单位 SGD），展示格式化走 `formatPrice`；结算金额保留两位小数。
- **时间**：统一 ISO 8601 / UTC 存储（如订单 `date`）。
- **状态**：使用字符串枚举（如订单状态 `待付款/待发货/待收货/已完成/已取消/退款中`），代码内常量集中管理。
- **索引等价**：商品索引（`productsBySlug`、`productsById`）由 `frontend/src/data/products-index.ts` 自动构建，禁止手写重复查找逻辑。
- **删除**：文件删除通过 git 进行（保留历史与审计痕迹），核心数据（商品、订单）不做物理覆盖式删除，改动前确认可回滚。

### 5.2 目标：PostgreSQL + MyBatis-Plus + Flyway（第一批落地）

- **选型**：数据库 PostgreSQL 16，ORM 使用 MyBatis-Plus（含分页插件、逻辑删除、乐观锁），表结构变更全部通过 Flyway 迁移脚本管理，禁止手工修改线上库（ADR 见 `docs/adr/0001-数据层选型-mybatis-plus.md`）。
- **表规范**：表名、字段名统一小写下划线命名；表名单数（`user`、`order_item`）；主键 `id`；时间字段 `created_at` / `updated_at`；软删除 `deleted`；乐观锁 `version`。
  - 注：`user` 为 PostgreSQL 保留字，用户表统一使用 `app_user`。
- **字段类型**：金额统一 `DECIMAL(18,2)`（对应 Java `BigDecimal`，JSON 过渡期用 number + SGD）；时间统一 `DATETIME` 存 UTC；状态字段使用 `TINYINT` 并配合枚举/字典说明。
- **索引**：普通索引 `idx_字段名`，唯一索引 `uk_字段名`；高频查询必须建索引，禁止在索引列上做函数运算。
- **软删除与审计**：核心业务表禁止物理删除（MyBatis-Plus `@TableLogic`），删除与变更保留审计痕迹；MyBatis-Plus `@Version` 处理并发更新。

## 6. Git 与分支规范

- 分支模型：
  - `main` 为发布分支；`develop` 为集成分支；`feature/xxx` 功能分支；`hotfix/xxx` 缺陷修复；`release/x.y.z` 发版分支。
  - 当前仓库仍在 `master` 上运行，迁移到 `main` 时须经发布流程（见 §14 待办）。
- 提交信息：遵循 Conventional Commits（`feat` / `fix` / `docs` / `refactor` / `test` / `chore`），尽量关联需求/缺陷编号，示例：`feat(products): import 23 BUZUD products from retail list`。
- 合并流程：
  - 禁止直接提交 `main`/`develop`；所有变更通过 PR/MR 合并。
  - 至少 1 人 Code Review，CI 通过且无高危问题方可合并。
  - 提交前必须通过 `npm run check`（lint + typecheck + build）。
- CI：`.github/workflows/ci.yml` 在 push/PR 时自动执行 lint、typecheck、build。

## 7. 测试规范

- 后端（Spring Boot）：关键服务模块（订单、购物袋、收藏、搜索）单测覆盖率目标 ≥ 70%，其余 ≥ 50%；新增业务逻辑必须配套单元测试。
- 前端：组件/页面关键逻辑配套测试；关键链路必须有自动化用例：搜索 → 商品详情 → 加购 → 结算 → 订单、收藏、登录/个人中心。
- 合并前必须通过：单元测试、接口联调、前端构建与冒烟检查、lint/format 检查。
- 当前测试基建为待办项（见 §14），新增时优先 JUnit 5（后端）与 Vitest/Playwright（前端）。

## 8. 文档与协作规范

- 每个应用必须提供 README：职责说明、本地启动、环境变量与配置、常用命令（已提供 `README.md`；后端详见 `backend/README.md`）。
- 接口变更同步更新接口文档；前端 API 客户端类型（`src/lib/api.ts`）与后端响应保持一致。
- 需求与规则变更同步更新本文档，保持需求、设计、代码一致。
- 重大架构或技术选型决策记录为 ADR，存档于 `docs/adr/`（已建目录，格式见其中 README）。

## 9. 版本规范

- 统一语义化版本（SemVer：`主版本.次版本.修订号`）。
- 版本号与后端 jar 版本（`backend/pom.xml`）、镜像 tag、发布分支、发布记录保持一致。
- 每次发版在发布分支上打 tag（`v1.0.0`），并更新变更记录。

## 10. 内容管理规范（BUZUD 特有）

- 商品：只允许零售价清单中的商品；`id` 用 SKU；`slug` 由英文名 + SKU 生成；图片放 `frontend/public/images/products/buzud-<sku>.jpg`。
- 分类：固定 5 类（快速检测试剂 / 智能手表 / 血压计 / 血糖管理 / 健康监测设备），新增分类需同步 `catalog.json`、`catalog-pages/all.json`、`menu-categories.json`。
- 管理后台：所有内容通过 `/admin/` 表单编辑（保存即生效）；商品与首页保留可选的 JSON 模式，仅高级操作使用。
- 导入流程：维护商品数据 → `scripts/update-buzud-menu.py` → `scripts/export-server-data.mjs` → 重启后端。
- 品牌：禁止在商品、分类、菜单中出现 IKEA 内容；首页与 SEO 文案为 BUZUD。

## 11. 常用命令

```bash
# 前端
cd frontend
npm run dev           # 开发服务器 http://localhost:3000
npm run build         # 生产构建
npm run lint          # ESLint
npm run typecheck     # TypeScript 检查
npm run format        # Prettier 自动格式化

# 后端（JDK 21，macOS 需设置 JAVA_HOME）

cd backend && ./mvnw -DskipTests package   # 打包
java -jar backend/target/ikea-server-0.1.0.jar
curl http://localhost:8080/api/v1/health  # 健康检查
```

## 12. 验证与发布流程

1. 修改后先本地验证：`npm run check`、`npm run format:check`；后端改动执行 Maven 测试/打包。
2. 数据类改动：执行 `node scripts/export-server-data.mjs`，重启后端，抽查对应页面/接口。
3. 前台抽查：首页（导航/轮播/榜单/feed）、所有商品、5 个分类页、商品详情（价格 SGD）、搜索、客户服务。
4. 管理后台抽查：登录 `/admin/`，各区块表单编辑并保存一次。
5. 功能分支提 PR → Code Review → CI 通过 → 合入 `develop` → 发版 `release/x.y.z` → 合入 `main` 打 tag。

## 15. 企业级改造路线（三批）

目标：从「JSON 数据 + 轻量后端」升级为可支撑企业级业务（订单、库存、支付、多端）的工程体系。技术选型按 ADR 记录，进度按 `docs/企业级改造路线图.md` 跟踪。

### 第一批：地基（数据、安全、分层、测试、CI）

- 数据层：PostgreSQL 16 + MyBatis-Plus + Flyway 迁移；实体/枚举/常量落地；JSON 数据迁移脚本。
- 安全：Spring Security + JWT（访问令牌 + 刷新令牌）、BCrypt 密码哈希、接口鉴权与权限模型、登录限流。
- 后端分层：`controller / service / mapper / entity / dto / constant` 落地；全局异常处理；`spring-boot-starter-validation` 参数校验；springdoc-openapi 生成 OpenAPI 文档。
- 测试：JUnit 5 + Testcontainers（数据库集成测试）；前端 Vitest（组件/单元）+ Playwright（E2E 冒烟）；覆盖率门禁（核心模块 ≥ 70%，其余 ≥ 50%）。
- 工程化：后端 Spotless/Checkstyle 接入 `mvn package`；CI 增加测试、覆盖率、镜像构建与推送。

### 第二批：工程化与可观测

- 前端：TanStack Query（服务端状态）、Zustand（客户端状态）、husky + lint-staged 提交门禁、pnpm workspace + Turborepo/Nx、i18n 国际化。
- 后端：Spring Boot Actuator + Micrometer/Prometheus 指标、结构化日志（JSON 输出）、Redis（缓存、会话、限流）。
- 监控：Grafana 看板、Sentry 前端错误监控、接口性能与错误告警。

### 第三批：架构演进

- 模块化单体拆分（订单/库存/支付/用户模块），条件成熟后再演进微服务。
- 消息队列：下单异步、超时取消、支付回调（RocketMQ/Kafka 选型记 ADR）。
- 部署：K8s + Helm 编排、环境管理（dev/staging/prod）、灰度发布。

### 决策记录

- `docs/adr/0001-数据层选型-mybatis-plus.md`：数据层选型（PostgreSQL + MyBatis-Plus + Flyway）。
- 后续每个重大选型（JWT 方案、消息队列、缓存、微服务拆分）均新增 ADR。
